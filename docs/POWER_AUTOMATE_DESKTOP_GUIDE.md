## Fase 06.2: respuesta JSON y excepciones

La plantilla local canónica [`automation/pad_action_template.ps1`](../automation/pad_action_template.ps1) incluye `automation_id = 'NO_DISPONIBLE'` dentro de `result` ante excepciones técnicas. La integración de PAD fue probada manualmente según el usuario, pero no se dispone de una exportación completa posterior a la última edición manual para comprobar igualdad exacta entre el bloque de PAD y esta plantilla. PAD sustituye `%ProyectoRuta%`, `%Workspace%` y `%Batch%` antes de ejecutar; utilice únicamente valores de confianza sin comillas simples, ya que la sustitución es textual. La plantilla invoca el intérprete de `.venv` directamente y no llama al lanzador anterior, cuyo `exit` puede terminar el proceso anfitrión. No cambia políticas ni realiza reintentos. `exit_code` dentro del JSON es el código de Python para una respuesta válida; la ejecución de PowerShell termina normalmente para que PAD pueda leerla. Un `REJECTED` válido conserva código 2.

El bloque captura fallos durante su ejecución y genera `FAILED` con `reason`, `distribution_status: NOT_PREPARED` y `errors`; cuando está disponible conserva el código nativo en `python_exit_code`. Valida JSON y coherencia entre estado y código. La salida estándar nativa vacía, malformada o incompatible se trata como fallo técnico; la salida estándar de errores nativa se descarta para no mezclarla con JSON ni divulgar datos sensibles. Para diagnóstico detallado usar los registros locales autorizados. El bloque no puede responder si PAD no inicia PowerShell, el script no se puede interpretar, se agota el tiempo o se interrumpe el proceso.

En PAD, desactivar reintentos automáticos y conservar una rama **Al producirse un error** para la acción PowerShell: registrar la incidencia y mostrar fallo técnico sin ejecutar la conversión JSON ni leer `CustomObject`. En la rama normal, comprobar que `PowershellOutput` no esté vacío antes de convertir. Mantener manejo de error de la conversión: ante JSON inválido, mostrar fallo técnico y detener esa rama sin usar `CustomObject` previo. Inicializar variables del resultado en cada ejecución para evitar reutilizar una respuesta anterior. Solo tras conversión exitosa evaluar `result.status`, `result.reason`, `result.distribution_status` y `exit_code`; conservar las cuatro notificaciones comerciales. `ScriptError` puede contener información técnica de la acción; no asumir que un código de Python 1 o 2 es una excepción PAD. `PREPARED` solo significa borrador local.

El usuario confirmó la prueba controlada de excepciones y la detención ante JSON inválido en PAD. Antes de actualizar PAD, comparar una exportación completa con la plantilla canónica; no se alteró la configuración funcional durante la corrección. Un fallo dentro del bloque y un fallo al iniciar PowerShell requieren ramas distintas, como se describe arriba.

## Condiciones y mensajes para Fase 06.1

Tras convertir `PowershellOutput` a objeto JSON, evaluar `result.status` y, cuando exista, `result.reason`. Para `SUCCESS`: «Procesamiento completo; distribución preparada para revisión» si `distribution_status` es `PREPARED`. Para `SKIPPED` con `ALREADY_PROCESSED_VERIFIED`: «Lote previamente procesado y verificado; no se preparó una distribución adicional». Para `FAILED` con `BATCH_NOT_RECEIVED`: «No se encontró el lote solicitado»; si `inbox_status` es `EMPTY`, añadir «La bandeja está vacía». Para `BATCH_INCOMPLETE`, solicitar revisar `READY.json`; para `HISTORY_UNVERIFIED` o `AMBIGUOUS_HISTORY`, detenerse y revisar las evidencias. Para `REJECTED`/`INVALID_BATCH`, revisar el registro de validación; para `TECHNICAL_ERROR`, revisar la alerta local. No tratar `PREPARED` como envío.

El código 0 sigue indicando `SUCCESS`/`SKIPPED`, el 2 `REJECTED` y el 1 `FAILED`. PAD puede tratar un código no cero como error de la acción: configurar su rama de manejo de errores para conservar `PowershellOutput` y `ScriptError` cuando estén disponibles. La consulta `--list-pending` es una opción separada de Python para una futura integración, no requiere modificar los parámetros actuales del script de PowerShell.

El usuario confirmó la ejecución del flujo y sus cuatro estados, notificaciones y manejo de excepciones en PAD. La igualdad completa del código probado con la plantilla local no está verificada. Consulte la referencia oficial de [acciones de PowerShell](https://learn.microsoft.com/en-us/power-automate/desktop-flows/actions-reference/scripting) y [variables de entrada y salida](https://learn.microsoft.com/en-us/power-automate/desktop-flows/manage-variables).

1. En la máquina autorizada, usar el flujo existente **AutoReport360 — Procesamiento Comercial** con el proyecto y su `.venv` instalados.
2. Definir entradas de texto `ProyectoRuta`, `Workspace` y `Batch`; usar rutas absolutas autorizadas y un nombre de lote sin separadores. Preparar previamente el lote y `READY.json` como indica [el diseño](AUTOMATION_DESIGN.md).
3. En **Ejecutar script de PowerShell**, configurar un tiempo límite suficiente según mediciones locales. Comparar la plantilla canónica con una exportación completa del bloque antes de actualizar PAD. Las variables interpoladas deben ser de confianza; la llamada usa el intérprete `.venv/Scripts/python.exe` sin activar el entorno.
4. Capturar `PowershellOutput` y `ScriptError`; convertir la salida JSON a objeto con la acción de conversión de JSON disponible. Verificar que el resultado existe y consultar `exit_code`, `result.status` y `result.distribution_status`. Las acciones de PAD pueden tratar una salida no cero como excepción; configurar su manejo de errores y registrar también `ScriptError`.
5. Considerar éxito local `SUCCESS` o `SKIPPED` con código 0; `REJECTED` usa 2 y `FAILED` usa 1. `PREPARED` no significa enviado. Guardar el resultado en el registro local autorizado y mostrar una notificación local sin datos sensibles.

El conmutador `-RecoverCorrupt` solo debe habilitarse tras aprobar la cuarentena del caso. No se cambia la política de ejecución global de Windows; la política de la organización debe permitir la ejecución del script. No introducir credenciales en variables o código.
